ARCHITECTURE (NanoClaw v2):
- Core principle: 'everything is a message.' Host and per-session agent container communicate only via two SQLite DBs (inbound.db host-writes / outbound.db container-writes).
- Inbound attachments: a channel adapter emits an InboundMessage whose content may carry attachments[]; the host extracts base64 attachment data to the session inbox as files. The agent's Read tool can render images but CANNOT interpret audio — so a voice note that arrives only as an audio file is effectively unusable to the agent.
- A channel-agnostic core helper already exists: src/transcription.ts exports transcribeAudioBuffer(buffer) (local faster-whisper first, OpenAI whisper-1 fallback, fixed placeholder on failure).
- WhatsApp is a NATIVE adapter; voice transcription for it was ALREADY implemented in the adapter's own inbound handler (transcribe the ptt voice note, drop the audio attachment, deliver transcript as message text).
- Telegram/Slack/Discord/Teams are CHAT-SDK-BRIDGE channels: they all share ONE inbound seam — src/channels/chat-sdk-bridge.ts messageToInbound() — which downloads every attachment generically (including Telegram 'voice' which @chat-adapter/telegram surfaces as a type:'audio' attachment with fetchData). chat-sdk-bridge.ts is a CORE/trunk file shared by all Chat-SDK channels.
- The ONLY current task is Telegram voice (row U1-TG). But the seam is shared.

OPTIONS:
- A (generic, at the shared bridge): in chat-sdk-bridge.ts messageToInbound, when an attachment is type:'audio', call transcribeAudioBuffer on its buffer, set the transcript as the message text, and drop the audio attachment (keep non-audio). This turns on voice transcription for ALL Chat-SDK channels (Telegram, Slack, Discord, Teams) at once. Lands in core.
- B (Telegram-specific): implement the same transcribe-and-replace only in src/channels/telegram.ts's onInbound wrapper (which post-processes the bridge's InboundMessage for Telegram). Narrow blast radius; duplicates the logic if another channel later wants it.
- C (host-side, after the adapter): transcribe in the host inbound path (e.g. router/session-manager) when writing an audio attachment to inbound.db — channel-agnostic AND covers native adapters too, but sits in a hotter, more central code path.

Note the WhatsApp adapter already does its own transcription, so option C would double-transcribe unless guarded.

### 2. DRY vs. Premature Generalization

Implementing this feature at the bridge level adheres to the DRY principle, avoiding code duplication that would occur if similar logic needed to be implemented separately for each channel. While B offers a narrow scope, it duplicates logic and could lead to maintenance burdens if other channels require transcription later.

### 3. Latency / Cost
Transcription is a subprocess and network call, potentially introducing latency. By placing this in the bridge, the latency is contained within the initial message handling for each channel but does not affect the host-side processes. To mitigate potential overload, transcription can be size or duration guarded to handle only manageable audio clips, reducing stress on the system and managing costs effectively.

### 4. Consistency with WhatsApp Approach
The existing WhatsApp implementation performs transcription at the adapter level. While Option A is a layer higher, it maintains a similar concept by ensuring that the agent receives only text, making it consistent in terms of the end-result: a text message instead of an audio file.

### 5. Failure Isolation
If transcription fails, Option A can be designed to handle such exceptions gracefully within the shared bridge, minimizing the impact. By implementing robust error handling and fallbacks (e.g., setting a placeholder text), the damage is contained within the transcription logic, preventing the entire message processing flow from stalling.

### 6. Testability and Reversibility
Centralizing the transcription logic in the bridge simplifies testing and debugging, as changes and improvements can be made in one place. Reversibility is straightforward, as any issues arising from the implementation can be isolated and rolled back in the core bridge file without touching multiple channel-specific implementations.
