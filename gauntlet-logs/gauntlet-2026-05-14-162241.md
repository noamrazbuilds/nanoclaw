## Failure Modes + Rollback

### 1. Merge conflict explosion during `git merge upstream/main`
**What breaks:** The 33 hot-conflict files produce unresolvable merge conflicts, especially in heavily-refactored files like `db.ts` → `db/*` where git can't track the rename+split.
**Rollback:** `git merge --abort` on the `v2-migration` branch. Production on `main` is untouched. Zero impact.
**Mitigation:** Don't use `git merge` for the deleted-then-split files. Instead, take upstream's version wholesale, then manually re-apply your patches using `git diff v1-production-snapshot -- src/db.ts` as a reference.

### 2. DB migration corrupts production data

## 6. Failure Modes + Rollback

### 1. Merge conflict explosion during `git merge upstream/main`
**What breaks:** The 33 hot-conflict files produce unresolvable merge conflicts, especially in files like `db.ts` → `db/*` where git can't track rename+split.
**Rollback:** `git merge --abort` on `v2-migration`. Production on `main` untouched. Zero impact.
**Mitigation:** For deleted-then-split files, don't fight git's merge. Take upstream's version wholesale, then manually re-apply your patches using `migration-plan.diff` as reference.

### 2. DB migration corrupts or loses data
**What breaks:** `migrate-v2.sh` or v2 DB migrations alter your SQLite database in a way that loses container configs, group state, or conversation history. Risk is elevated if you added custom columns/tables to `db.ts`.
**Rollback:** Restore from pre-cutover backup: `cp ~/nanoclaw-v1-backup-*/nanoclaw.db ~/nanoclaw/ && git checkout v1-production-snapshot && pm2 restart nanoclaw`. Recovery: ~2 minutes.
**Mitigation:** Run migration against a COPY first (Phase 3). Specifically verify your custom schema extensions survive the migration. If `migrate-v2.sh` assumes vanilla v1 schema, you may need to run it selectively or patch it.

### 3. IPC replacement breaks channel customizations
**What breaks:** v2 replaced `src/ipc.ts` with a different communication mechanism. Your sticker/reaction/document sending patches use the old IPC API. They compile (types might be loose) but fail at runtime.
**Rollback:** `git checkout v1-production-snapshot && pm2 restart nanoclaw`.
**Mitigation:** Scout phase explicitly maps the IPC replacement. If v2's IPC doesn't support your message types, this is a design problem discovered in Phase 0 — before you've invested porting effort. You may need to extend v2's IPC, which is additional work but better discovered early.

### 4. Channel skill-branches don't load forked customizations
**What breaks:** v2 expects channels from upstream skill-branch URLs. Your forked channel repos aren't found or the skill-branch loader hardcodes upstream URLs.
**Rollback:** Same as above.
**Mitigation:** Scout phase identifies how the skill-branch loader discovers channels (config file vs hardcoded). If config-based, point at your forks. If hardcoded, you need a config override or a patch to the loader — identified before cutover.

### 5. `migrate-v2.sh` makes assumptions your fork violates
**What breaks:** The migration script assumes vanilla v1 layout. Your 24 added files, modified configs, or non-standard DB schema cause it to fail or silently skip steps.
**Rollback:** `git merge --abort` or `git checkout v1-production-snapshot` depending on phase.
**Mitigation:** Scout reads the script in Phase 0 and documents every assumption. You'll likely end up running it selectively, not wholesale — using its logic as a guide for manual steps where your fork diverges.
