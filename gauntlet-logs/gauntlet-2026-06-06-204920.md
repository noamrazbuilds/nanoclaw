ARCHITECTURE (NanoClaw v2):
- Host (Node) and per-session container (Bun) talk ONLY via two SQLite files per session: inbound.db (host writes/container reads) + outbound.db (container writes/host reads). The container CANNOT write the central host DB (data/v2.db; not mounted in container).
- Agent tool calls (incl. MCP tools: Drive/Gmail/Sheets) run INSIDE the container via the Claude Agent SDK. Credentialed MCP calls are proxied by an external OneCLI gateway (injects secrets; has its own request log).
- The container ALREADY has SDK PreToolUse/PostToolUse hooks firing on every tool call (today they record the in-flight tool to outbound.db for stuck-detection) — so the container already observes every tool call + success/failure, and knows its task_id/run_id.
- C5's task_audit_log (task create/update/delete, host-side central DB) is already settled. THIS decision is ONLY the per-run TOOL-CALL ledger C6 consumes.
- v1 wrote a host-side gws-audit.jsonl by wrapping gws calls; in the 2026-05-18 incident it proved fragile (stopped writing) and only covered gws calls.

OPTIONS:
- A: ledger built on the container's existing PreToolUse/PostToolUse hooks — each call writes (tool, args summary, status, ts, task_id, run_id) to a new table in the session's outbound.db; host scheduler reads it at run finalization. Reuses existing seam; covers ALL tools; run-scoping trivial. Con: per-session location; container writes its own ledger.
- B: host-side MCP wrapping layer writing host_op_audit_log in central data/v2.db (v1-style). Con: in v2 tools run in-container so host has no interception point except OneCLI; covers only OneCLI-proxied calls; new plumbing that fights v2's model.
- C: use OneCLI gateway's request log as the ledger source. Con: only credentialed/proxied calls (misses local tools like Read/Bash); couples C6 to OneCLI; run-scoping needs OneCLI to carry a task tag.

### (2) Fit with v2 Container-Executes-Tools + Two-DB Model

This maintains the separation of responsibilities and aligns with the current architecture without introducing new complexities.

### (3) Reliability
The reliability of Option A is bolstered by its integration into the existing hooks that have already been used for stuck-detection. Given that the container directly writes to its outbound.db, the risk of missing logs is minimized compared to v1's host-side logging, which had a failure incident. This direct logging mechanism is inherently more reliable because it does not depend on external interception points that could fail or be bypassed.

### (4) Run-Scoping Precision / Concurrent-Run Isolation
Option A allows for precise run-scoping and isolation because each session's tool-call ledger is written directly to its corresponding outbound.db. This ensures that logs are automatically scoped to the specific session, avoiding any potential cross-contamination or ambiguity between concurrent runs.

### (5) Blast Radius + Reuse of Existing Seams
By reusing the existing PreToolUse/PostToolUse hooks, Option A minimizes the introduction of new failure points into the system. Leveraging these established hooks reduces the blast radius of potential implementation errors and takes advantage of the already functioning seam for capturing tool invocations. This reuse promotes consistency and reduces the complexity of the implementation.

### (6) Trust Model
The crux of the decision lies in whether trusting the container to write its own tool-call ledger is significantly better than relying solely on its self-reported success summary. While both rely on the container's integrity, having a detailed ledger of tool calls (including arguments, status, and timestamps) offers a more granular level of verification and supports independent checks by the host scheduler. This additional layer of logging provides a safeguard against fabricated success summaries by requiring consistency between the ledger and the reported outcomes.

Ensuring the container's integrity through other security measures is essential.
