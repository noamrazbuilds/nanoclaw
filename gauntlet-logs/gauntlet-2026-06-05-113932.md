This evaluation assesses each option against the specified criteria.

*   **Option B (Inbound Message):** This is a perfect fit for the core principle. It treats the reaction as what it is: a message. This maintains a single, simple paradigm for the agent: "I receive information from the user via the `inbound.db`." The high potential cost is a serious practical concern, but it is a solvable engineering problem via filtering, not an architectural flaw.
*   **Option C (Hybrid):** This is a compromised fit. By implementing both patterns, it acknowledges that reactions *are* messages but simultaneously creates a secondary, non-message-based pathway. This introduces architectural ambiguity and complexity.

**Conclusion:** Option B is the only choice that fully respects the system's core architectural principle. The cost issue is a practical implementation detail, not a fundamental design mismatch.

#### 2. Blast Radius

*   **Option A (Passive Table):** **High Blast Radius.** This option requires adding a new `onReaction` callback to the core `ChannelSetup` adapter contract. This is a significant change. It touches the central channel registry and forces every single channel adapter implementation (current and future) to account for this new, optional callback. All changes are contained within the WhatsApp adapter and the central `router.ts` (for filtering). No core contracts are altered.
*   **Option C (Hybrid):** **Highest Blast Radius.** This option combines the downsides of both, requiring the new `onReaction` callback from Option A *and* the complex routing/filtering logic from Option B.

**Conclusion:** Option B is the clear winner on this front. It isolates the change and avoids polluting the core adapter contract, which is a major software engineering benefit.

#### 3. Real-Time Need for Reactions

The agent does not typically need to be woken up *the instant* a user reacts with a 👍. However, it absolutely needs access to that reaction as context when it next formulates a response.

*   **Option A (Passive Table):** Fails to provide timely context. The agent would have to be programmed to remember to query the reactions table for every message it has sent, which is inefficient and unnatural. It creates a blind spot.
*   **Option B (Inbound Message):** Provides perfect contextual awareness. When the agent wakes for any reason (e.g., a new text message), it can scan its `inbound.db` and see the full sequence of events, including "User sent message Z," "I sent message Y," "User reacted with 👍 to message Y," "User sent message X." *   **Option C (Hybrid):** Over-engineers the solution by providing both real-time wakes (which are rarely needed) and a passive table (which is an awkward way to consume context).

**Conclusion:** The agent needs reactions for *context*, not necessarily for *real-time interruption*. Option B, implemented so that reaction-messages are delivered but do not trigger a wake by default, perfectly serves this need.

#### 4. Reversibility & Migration Risk

*   **Option A (Passive Table):** Moderately reversible. You can remove the `onReaction` callback, but this constitutes another breaking change to the core contract. The database migration to add the `reactions` table would also need to be managed.
*   **Option B (Inbound Message):** Highly reversible. To disable the feature, you simply stop synthesizing the reaction messages in the WhatsApp adapter. There are no database schema changes to `data/v2.db` and no core contract changes to revert. It's a logic-only change.

### Detailed Analysis of Options

This analysis evaluates each option against the five specified criteria.

**Conclusion:** Option A is the most pragmatic choice, prioritizing operational stability and cost control over dogmatic adherence to a principle. The cost risk of Option B is too severe to ignore.

#### 2. Blast Radius

*   **Option A (Table):** The blast radius is focused on the core `ChannelSetup` contract. Adding a new `onReaction` callback requires touching `channel-registry.ts` and the host wiring. *   **Option B (Message):** The blast radius on the *contract* is minimal, as it reuses the existing `onInbound` callback. However, the practical blast radius is larger. The WhatsApp adapter needs new logic to synthesize these messages. More importantly, to control the cost issue, a new filtering or debouncing mechanism would be needed upstream of the `router.ts`, which is a significant new piece of logic in the critical inbound path.
*   **Option C (Hybrid):** This option has the largest blast radius, as it requires implementing the contract change from A, the synthesis logic from B, *and* an entirely new configuration and rules engine.

**Conclusion:** While Option A touches a core contract, its impact can be managed as a non-breaking, optional addition. Option B's "low" blast radius is deceptive, as it necessitates a complex and risky filtering system to be viable.

#### 3. Real-Time Need for Reactions

The core question is whether an agent needs to be *interrupted* by a reaction, or if it just needs awareness of it.

*   For most use cases (e.g., gauging sentiment, seeing acknowledgement), awareness is sufficient. The agent can query for reactions on a message before formulating its next response. A passive, query-based model (Option A) serves this perfectly.
*   A minority of use cases might benefit from real-time events (e.g., "React with ✅ to confirm your attendance"). Option B would handle this natively. However, such workflows can also be handled by Option A; the agent would simply need to be prompted to periodically poll for reactions to a specific message after asking for them.

**Conclusion:** The majority of foreseeable agent needs are met by the on-demand query model of Option A. The need for true real-time, event-driven reaction handling is not compelling enough to justify the cost and complexity of Option B.

#### 4. Reversibility & Migration Risk

*   **Option A (Table):** This is highly reversible and extensible. The reaction data is stored cleanly in its own table, decoupled from the conversational history. If we later decide we need event-driven reactions, we could build a service that reads from this table and synthesizes messages, effectively migrating towards B or C. It's an additive, low-risk foundation.
*   **Option B (Message):** This is difficult to reverse. Once reactions are injected into the `inbound.db` as messages, they become a permanent part of the conversation history. Extracting or changing how they are represented later would be a complex data migration task.
*   **Option C (Hybrid):** This would be the most difficult to unwind, having two intertwined systems.

**Conclusion:** Option A provides the most future-proof and least risky path. It does not foreclose future changes.

#### 5. Impact of Outbound-Already-Native

This frames reactions as a consistent "metadata layer" that sits alongside the primary message stream, accessed via tools for both reading and writing. Option B would create an undesirable asymmetry where reactions are sent as tool calls but received as system messages.

**Conclusion:** The existing outbound implementation strongly favors Option A for architectural consistency.

*   For most use cases (e.g., gauging sentiment, seeing acknowledgement), awareness is sufficient. The agent can query for reactions on a message before formulating its next response. A passive, query-based model (Option A) serves this perfectly.
*   A minority of use cases might benefit from real-time events (e.g., "React with ✅ to confirm your attendance"). Option B would handle this natively. **[REVISED]** Option A can support these workflows via the agent polling for reactions on a specific message. However, this is not a trivial workaround. It pushes complexity into the agent's logic, requiring it to manage state, timers, and polling intervals. While this is a real development cost, it is a known, bounded complexity within the agent's domain, which is preferable to the unbounded operational cost and platform-level complexity of Option B or C.

**Conclusion:** The majority of foreseeable agent needs are met by the on-demand query model of Option A. The need for true real-time, event-driven reaction handling is not compelling enough to justify the cost and architectural complexity of Option B.

#### 4. Reversibility & Migration Risk

*   **Option A (Table):** This is highly reversible and extensible. The reaction data is stored cleanly in its own table, decoupled from the conversational history. If we later decide we need event-driven reactions, we could build a service that reads from this table and synthesizes messages, effectively migrating towards B or C. It's an additive, low-risk foundation.
*   **Option B (Message):** This is difficult to reverse. Once reactions are injected into the `inbound.db` as messages, they become a permanent part of the conversation history. Extracting or changing how they are represented later would be a complex data migration task.
*   **Option C (Hybrid):** This would be the most difficult to unwind, having two intertwined systems.

**Conclusion:** Option A provides the most future-proof and least risky path. It does not foreclose future changes.

#### 5. Impact of Outbound-Already-Native

This is a critical factor. The system already has a precedent for handling reactions outside the "everything is a message" paradigm.

*   The agent sends reactions via an `add_reaction` MCP tool, not by outputting a special "reaction message." This is an action, or a metadata operation, not a standard message.
*   Choosing Option A creates a clean symmetry:
    *   **Outbound:** Agent uses a `tool` to add reaction metadata.
    *   **Inbound:** Agent uses a `tool` (e.g., a new `get_reactions` query) to read reaction metadata.

This frames reactions as a consistent "metadata layer" that sits alongside the primary message stream, accessed via tools for both reading and writing. Option B would create an undesirable asymmetry where reactions are sent as tool calls but received as system messages.

**Conclusion:** The existing outbound implementation strongly favors Option A for architectural consistency and coherence.

### Recommendation: Option A

**Option A is the recommended path forward.** It is the most pragmatic, operationally safe, and architecturally consistent choice. It correctly prioritizes cost control and stability over philosophical purity, especially when a precedent for this "impure" approach already exists in the outbound flow. It provides a solid, low-risk foundation that can be extended later if true real-time needs emerge.

#### The Single Biggest Risk of This Choice

The biggest risk is **feature velocity drag and agent complexity for reaction-gated workflows.** **[REVISED]** If a high-priority product requirement emerges for agents that must react *immediately* to a specific emoji, the polling/query model of Option A would be clumsy. The complexity of implementing reliable, performant polling within the agent itself might become a significant development bottleneck, forcing a re-architecture to a more event-driven approach.

#### What Would Change My Mind

A **firm, validated product requirement for sub-second, event-driven agent workflows triggered exclusively by inbound emoji reactions.** If this were defined as a mission-critical, non-negotiable feature for a major client, the cost/complexity trade-off would shift, making the pain of implementing a filtered version of Option B or C a necessary business decision. Without such a requirement, it constitutes premature optimization and unnecessary risk.

### Unresolved Tensions
