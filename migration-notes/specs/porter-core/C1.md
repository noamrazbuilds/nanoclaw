## Behavioral spec (one paragraph)
When the Anthropic SDK signals credit-balance exhaustion — via either (a) non-zero exit with credit-error text in stderr, or (b) the SDK quirk of returning the API error as a "successful" text result during exit-0 streaming — the system **swallows the raw error from user delivery**, drops a `_close` IPC sentinel into the container's input dir so it exits promptly (no 30-min idle wait), notifies the user in chat (`"Hey man, Anthropic credit balance ran dry. No worries — I'm re-running that on Gemini. Should be right back."` for interactive messages, `"Anthropic credit balance ran dry mid-task. Re-running this scheduled task on Gemini."` for scheduled tasks — but skip notification if `suppress_chat_output` is set, per C4), and **re-runs the same request exactly once** in a fresh isolated session (no session-resume — the SDK would just bounce back to the same Anthropic model) with `model: 'gemini-2.5-flash'` (configurable via per-group `containerConfig.fallbackModel`, global default in `DEFAULT_FALLBACK_MODEL`). If the fallback also fails, the error is recorded normally (no second retry). For non-Anthropic primary models, the SDK's own `fallbackModel` is suppressed so a credit-retry on Gemini can't bounce back to a Claude model. The reason: Anthropic credit balance is non-deterministic from the user's perspective (refilled monthly but consumable by background tasks); without this fallback the agent appears silently unresponsive for hours during credit gaps. Production evidence: this exact mechanism averted user-visible failures across 14+ days of credit issues in May 2026 (until C6 (honest-failure enforcement) surfaced a separate fabrication problem when the fallback itself broke during the hotfix window).

## v2 hook point(s)
v2 invokes the SDK **inside the container** (`container/agent-runner/src/poll-loop.ts:170 config.provider.query(...)`), so the v1 host-side wrap-and-sniff pattern doesn't map directly. The port splits across host + container:
- **Container-side detection** (`container/agent-runner/src/poll-loop.ts:183-213`, both the `try` result path and the `catch` block): import `isCreditError` and inspect `result.text` + `err.message`. On match, emit a structured outbound row signaling "credit error — please retry with fallback" (recommend a new outbound `kind: 'credit_error'` with a `fallback_model` field, or reuse `kind: 'chat'` with a discriminator field — Porter decides per OQ#1 below). Suppress the raw error from normal outbound delivery.
- **Host-side retry orchestration** (`src/router.ts` or `src/session-manager.ts` outbound routing path): on `credit_error` row, send user-visible notification (verbatim copy from v1), kill the current container (it should already be exiting from the sentinel), and re-spawn with the fallback model (`wakeContainer` + per-message model override — verify v2's session-spawn API supports this; if not, schema change needed).
- **Scheduled-task path** (`src/modules/scheduling/actions.ts` or `index.ts`): same detection + retry; respect `suppress_chat_output` for the notification skip; cap at one retry per task run.
- **Shared utility**: extract `isCreditError(text)` into `src/credit-error.ts` (~20 LOC, no other deps). Imported by both container (via container-runner's mount) and host. U4 (`oauth-refresh.ts`) currently owns this function — decouple so C1 isn't blocked on U4.

## Decisions / open questions
1. **Outbound signaling shape** (container → host): new `kind: 'credit_error'` vs. discriminator field on existing `kind: 'chat'`? Recommend: **new kind**. v2's outbound vocabulary (`chat | edit | reaction | ask_question | card`) treats kinds as the structural discriminator; adding `'credit_error'` matches that grain. Avoids overloading `chat` with non-chat semantics.
2. **Provider switch mechanism:** v2's `container_configs.model` is set at session-spawn time, and the container binds to one provider via `provider-container-registry.ts`. For the retry: either (a) spawn a new container with `provider: 'gemini'` (provider-switch on respawn — clean, but requires provider plumbing), or (b) keep container-as-Claude and let SDK fall back via its own `fallbackModel: 'gemini-2.5-flash'` directive (matches v1; simpler if SDK supports cross-provider fallback in v2). Porter to validate (b) is viable; if not, (a) is the alternative.
3. **`fallbackModel` schema:** v1 has `containerConfig.fallbackModel`; v2's `container_configs.model` is a single column. Either extend schema with `fallback_model` column (migration) or store as JSON on an existing flexible field. Hardcoded `DEFAULT_FALLBACK_MODEL = 'gemini-2.5-flash'` is acceptable for v1.0 parity; per-group override can come later.

## Notes for Porter
