# C3 — Agent drift safeguards (session rotation + skill-hash invalidation)

## Source (v1)
- Constants: `docs/v1-fork-reference/src/container-runner.ts:40-41` — `MAX_SESSION_AGE_MS = 24 * 60 * 60 * 1000` (24h).
- Hash function: `docs/v1-fork-reference/src/container-runner.ts:47-66` — `computeSkillsHash()`. SHA-256 walk over `container/skills/` dir; hashes file path + content for every regular file (excludes `__pycache__`); returns 16-hex-char prefix.
- Invalidation gate: `docs/v1-fork-reference/src/index.ts:578-608` (runs before each `runAgent` invocation in the message loop, before any container spawn). Reads `sessions.created_at` and `sessions.skills_hash`; if age > 24h OR `currentHash !== row.skills_hash`, deletes the session row + clears the in-memory `sessions[sessKey]` map entry, forcing fresh session creation on next spawn.
- Schema: v1 `sessions.created_at` + `sessions.skills_hash` columns (added via `ALTER TABLE` at `src/db.ts:178, 184`).
- Origin: documented in `reference_agent_drift_fixes.md` memory — added to prevent observed behavioral drift where long-running sessions deviate from their original instructions, especially after silent skill updates.

## Behavioral spec (one paragraph)
Before every container wake for a given agent group, the orchestrator checks two invariants on the existing session (if any) and **invalidates** it (delete row, clear in-memory map, force fresh session on spawn) if either fails: (1) **age cap** — session `created_at` is no more than 24h ago, OR (2) **skill-set integrity** — current hash of the container-skill files matches the hash stored on the session at creation. The age cap exists because LLM session context accumulates drift over time (tool-use patterns, naming conventions, hallucinated state) — a hard rotation every 24h bounds drift to ≤1 day. The skill-set integrity check fires when the user (or skill-update script) modifies any file under `container/skills/`: the session's instruction surface has changed, so resuming the old session would mix old-and-new instructions in unpredictable ways. Together these are **safety controls**, not perf optimizations — they trade a small "cold session" penalty (re-establish context on first turn after rotation) for guaranteed bounded behavioral drift. The reason: agent drift compounds; without bounds, a long-running session can subtly forget or re-invent rules that were established at start.

## v2 hook point(s)
- **Schema migration**: new column on `sessions` table — `skills_hash TEXT NOT NULL DEFAULT ''`. Migration file: `src/db/migrations/<NN>-session-skills-hash.ts`. v2 already has `sessions.created_at` (verified at `src/db/sessions.ts:9`), so no addition there.
- **Hash utility**: port `computeSkillsHash()` to `src/skills-hash.ts` (new file, ~20 LOC, no deps beyond `crypto` + `fs` + `path`). Must hash the **resolved skill set for the session's agent group**, not all skills globally — v2's `container_configs.skills` JSON column selects per-group skill sets (SKILL_REGISTRY pattern). The hash should reflect (skill names selected) + (file content of selected skills). See OQ#1 below.
- **Invalidation gate**: `src/container-runner.ts:wakeContainer` (line ~95) or upstream in `src/session-manager.ts` where session lookup happens. Add the check BEFORE the existing session-resume path — if invalid, delete via `src/db/sessions.ts` and let the spawn path create a fresh session.
- **Session creation**: at session-row insert in `src/db/sessions.ts:9`, write `skills_hash = computeSkillsHash(agentGroupSkills)` so the value is set at creation time for later comparison.

## Decisions / open questions
1. **Skill-set hash scope** (the key v1→v2 divergence): v1 hashes ALL files under `container/skills/`, globally. v2 has per-group skill selection via `container_configs.skills` (JSON column). Two options: (a) preserve v1's pattern — hash all skills globally (sessions invalidate on ANY skill change, even ones not in this group's set); (b) hash only the resolved set for THIS group (sessions invalidate only when skills affecting this group change). **Recommend (b)** — more precise, fewer spurious invalidations. Cost: need to read `container_configs.skills` to resolve the set before hashing. (a) is acceptable if (b) is hard to plumb.
2. **24h cap value**: v1 uses exactly 24h. Reasonable per "bound drift to ≤1 day". OQ: is this configurable per-group? Recommend: **constant for v1.0 parity; expose as `container_configs.session_max_age_h` if a use case for per-group override emerges**.
3. **Invalidation logging**: v1 logs at INFO level (`'Invalidating session'` with reason). Preserve — these logs are diagnostic when investigating context loss. Tag `reason` as one of: `age` | `skills_changed`.
4. **First-message-after-rotation UX**: when a session is invalidated and a fresh one starts, the agent loses its conversational context. v1 doesn't notify the user (silent rotation). Consider whether v2 should — but probably no, the cost is invisible most of the time and notification would be noisy. **Recommend: silent, matching v1**.
5. **Race with skill-update scripts**: if the user runs an update that modifies `container/skills/` while a session is mid-run, the hash diff fires on the next wake. This is correct behavior (the in-flight turn finishes; next turn rotates) but worth documenting.

## Notes for Porter
- **This is a security control**: prioritize correctness over cleverness. Stale sessions silently drifting is the failure mode this prevents.
- **Hash output truncation**: v1 truncates the SHA-256 hex to 16 chars. Preserve — full 64-char hex inflates the DB column needlessly; 16 chars (64 bits of entropy) is more than enough for collision avoidance across O(10) sessions.
- **The `created_at` field is already in v2's sessions table** — don't re-add. Just add `skills_hash`.
- **`reference_agent_drift_fixes.md`** is the historical context memory; read for the production rationale that drove these safeguards.
- **Test fixtures**: (1) session age 23h → not invalidated; (2) session age 25h → invalidated with reason=`age`; (3) skill file content changes → invalidated with reason=`skills_changed`; (4) skill file added but not in this group's set, under option (b) → not invalidated; (5) skill set changes (group adds a new skill) → invalidated with reason=`skills_changed`.
