## Behavioral spec (one paragraph)
At the end of every scheduled-task run, **before** the scheduler accepts the agent's self-reported "success" status, the executor inspects the run's tool-call ledger (rows in C5's `host_op_audit_log` scoped to this task's run window + source tags) and verifies that the task's declared "required tool signatures" were actually invoked successfully. If the agent reports success but the required tool surface was never touched, the executor **overrides the result to `'error'`** with a synthetic explanation (e.g., `"task reported success but invoked zero of the required tool surface: [sheets.values.get, sheets.values.clear|update]"`) and routes through the normal error path (which may trigger retry, user alert, log entry — task-config dependent; don't add new retry logic here). The required-tools declaration lives on the task row as a new JSON field, e.g., `[{"op_match":"sheets.values.get","min_success":1},{"op_match":"sheets.values.(clear|update)","min_success":1,"match":"regex"}]`. Tasks without a declaration get **lenient behavior** (trust self-report, log a warning) — strict default would break every existing task on day one. The reason: in a system where the agent self-reports success, LLM pattern-completion + prior-context bleed + ambiguous tool errors can produce fabricated success summaries with no real tool invocations. Prompt-level retries can't catch this because the agent's own report IS the signal. Only system-level inspection of the tool-call ledger does — this row is that inspection.

## Decisions / open questions
1. **Declaration schema** (`required_tools_json` shape): proposed in the behavioral spec. Allows exact-match (`op_match: "sheets.values.get", match: "exact"` implicit), regex (`match: "regex"`), and minimum-count thresholds. Open: should it support negative constraints ("MUST NOT touch gmail.delete") as well? Recommendation: **add later if needed** — start with positive constraints only.
2. **Default behavior** for un-declared tasks: lenient (trust self-report + log warning) vs. strict (override every claimed success without declaration). **Recommend lenient with metrics** — every un-declared task produces a structured warning row. Track over time, migrate to strict declarations task-by-task. Strict-by-default would break every legacy task on cutover.
3. **Ledger-query scoping**: this is the C5 OQ #2 manifestation. C6 needs a way to filter audit entries to "this task's run". Two paths: (a) C5's `host_op_audit_log` includes a `source_task_id` field set by the MCP wrapping layer when the call originates from a scheduled-task agent, OR (b) C6 uses a coarser timestamp-window match. (a) is precise but requires plumbing; (b) is approximate but lossless. **Recommend (a)** — without source-task scoping, concurrent task runs would cross-contaminate ledgers. Coordinate with C5 spec author.
4. **Synthetic-error format**: the explanation string must be parseable for downstream consumers (alerting, logs). Recommendation: prefix with `[honest-failure-override]` so it's grep-able; structured JSON in the `error` column would be cleaner but breaks `error TEXT` schema. Format: `[honest-failure-override] task reported success but invoked zero of: [tool1, tool2]; check audit log task_id=<id> window=<start..end>`.
5. **Override-on-already-failed-runs:** if the agent reports `error` AND the required tools weren't invoked, do we leave the agent's error or replace with the honest-failure error? **Leave the agent's** — they're already failing; double-stamping just adds noise.
