## Behavioral spec (one paragraph)
The arena grading pipeline scores responses from competing model bots in the Model Arena (F1). Grading is a structured-output task (parse N responses → produce ranking + per-response scores) where the grader's job is **comparison and judgment**, not novel generation — a task class where Sonnet is empirically sufficient and ~5× cheaper than Opus. Hard-coding `GRADER_MODEL` as a single constant (vs. per-bot config) reflects the design intent: the grader is a single, stable role across all arena runs; per-arena-bot model selection happens separately via each bot's `model` field in `ARENA_BOTS`. The grader is invoked once daily (`GRADING_CRON='0 2 * * *'`) on the previous day's accumulated arena sessions; cost reduction here compounds over time. The reason this exists as its own row (separate from F1's broader re-host): C2 captures the **pattern** — "single-role agent → cheap stable model" — which generalizes beyond the arena grader (any future quality-scoring, summarization, or classification pipeline benefits from the same swap).

## v2-native equivalent that might suffice?
**PARTIAL-OVERLAP.** v2's `container_configs.model` + `effort` columns (commit `ad5d4d2` per memory) provide the infrastructure for per-agent model selection. But there's no v2 native concept of "role-bound model" (e.g., "always use Sonnet for grading regardless of which group is asking") — that's what the hardcoded `GRADER_MODEL` constant gives. So the v2 mechanism is leveraged for general-purpose model selection, but the grader-specific binding is a constant in code.

## Decisions / open questions
1. **Hardcoded constant vs. config-driven** (Porter-Core decision): keep `GRADER_MODEL` as a constant in `arena-config.ts` (matches v1, simplest), OR push to a new config table or env var (more flexible, lets ops swap without code change). **Recommend: keep constant.** Cost-reduction swaps happen ~once per year; flexibility cost > value. If a future row demands per-environment grader override, revisit then.
2. **Generalize the pattern?** The "single-role agent → cheap stable model" pattern could be encoded in v2 as a `role_model_overrides` config map (`{ grader: 'sonnet', summarizer: 'haiku', ... }`). **Recommend: NO**, premature abstraction. Only one role exists today (grader). Add the abstraction if/when a second role emerges.
3. **Cross-row coupling with F1:** since the grader code lives entirely inside the arena module, C2 is implementable only as part of F1 (re-host the arena, including the constant). Sequencing: **F1 owns the merge; C2 is the spec that documents the cost-reduction decision so F1 doesn't accidentally regress to Opus**.
