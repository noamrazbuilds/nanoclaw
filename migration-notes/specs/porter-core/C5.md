## Behavioral spec (one paragraph)
Every mutation to a scheduled task — create, update, delete — appends a row to `task_audit_log` with timestamp (ISO-8601), task ID, action type, source identifier, before-snapshot JSON, after-snapshot JSON. The source tag captures origin: `'ipc'` for agent-initiated changes via scheduling MCP tools, `'manual:claude-code'` for direct DB edits during maintenance, arbitrary tagged sources for other origins. Update audits only fire when a "significant" field changes (`prompt`, `schedule_type`, `schedule_value`, `model`) — incidental writes like `last_run` don't generate noise. The table is append-only — never UPDATEd or DELETEd by app code. Indexed by task_id (per-task history) and timestamp (range scans). The reason: when an autonomous agent can modify its own scheduled tasks, mutations vanish into history without a forensic trail; the audit log IS that trail. Production-proven: in the 2026-05-18 concert incident, the log was the definitive evidence that the agent had not deleted the spreadsheet via any audited path (a key triage finding that ruled out one entire class of cause). **Post-incident broadening (2026-05-18):** scope must also cover host-side data-touching ops (Drive/Gmail/Sheets/Calendar mutations) because the existing `gws-audit.jsonl` host-side log proved fragile (stopped writing entries the same day). Same shape, polymorphic discriminator.

## v2 hook point(s)
**Task audit (v1 parity):**
- New migration: `src/db/migrations/<NN>-task-audit-log.ts` creating `task_audit_log` table + indexes.
- Writer helper: `logTaskAudit(db, taskId, action, source, before, after)` added to `src/modules/scheduling/db.ts` (sibling of `insertTask`, `cancelTask`).
- Call sites: every mutation function in `src/modules/scheduling/db.ts` and `src/modules/scheduling/actions.ts` — wrap with audit write. v2 tasks live in `messages_in` rows with `kind='task'`; mutations happen via `insertTask`, `cancelTask`, `pauseTask`, `resumeTask`, recurrence-handler row updates. Preserve v1's "significant field only" guard for updates so the table doesn't fill with `last_run` noise.

**Host-op audit (post-incident broadening — see OQ#1):**
- New migration: `src/db/migrations/<NN+1>-host-op-audit-log.ts` creating `host_op_audit_log` table.
- Proposed schema: `(id INTEGER PK AUTOINCREMENT, timestamp TEXT, operation TEXT, resource_type TEXT, resource_id TEXT, source TEXT, params TEXT (JSON), result_status TEXT, result_detail TEXT)`. Resource types: `'drive_file'`, `'gmail_message'`, `'sheet'`, `'calendar_event'`. Operations: `'create'|'update'|'delete'|'trash'|'clear'|'write'`.
- Writer hook: integrate into the MCP wrapping layer for gws + any direct host-side data-mutation surface. Every write goes both to `host_op_audit_log` AND to the existing `gws-audit.jsonl` (redundancy until one is proven reliable). Failure to write the audit row should fail the operation (or at least log loudly) — don't preserve v1's "best effort, ignore errors" pattern for the host-op path.

## v2-native equivalent that might suffice?
**DOES-NOT-EXIST.** Verifier-2 (2026-05-18) re-confirmed no audit-table equivalents in v2 main. The host-side `gws-audit.jsonl` is partial coverage (gws-MCP-mediated calls only, and proved fragile in the 2026-05-18 incident). v2 needs a v1-equivalent scheduled-task audit + a new host-op audit to cover the incident-identified gap.

## Decisions / open questions
1. **Scope split: one table or two?** Option (a) — single polymorphic table with `entity_type` discriminator (`'task' | 'host_op'`). Option (b) — two separate tables. **Recommend (b) — two tables.** Different shapes (task = before/after JSON of full task row; host-op = operation + resource + params), different query patterns (per-task history vs. per-resource history), different write rates (mutations are rare; host-ops are continuous). Mixing them complicates both schemas.
2. **`task_run_logs` port:** v1 has a separate `task_run_logs` table for per-run results. **Not in C5 scope strictly**, but C6 (honest-failure enforcement) needs a per-run record to attach the tool-call ledger to. Recommend: include `task_run_logs` port in C5 as a sibling table (no behavior change, just preservation) so C6 has the foundation it needs.
3. **Audit-write failure mode:** v1 ignores audit-write failures (try/catch swallow). For host-op audit (where forensic integrity matters), should we fail-loud or fail-soft? Recommend: fail-loud — at minimum log at ERROR level; consider configurable strict mode that fails the underlying operation if audit write fails.
4. **Source-tag taxonomy for host-op audit:** finer-grained (`'mcp:gws_drive_files_delete'`) vs. coarser (`'mcp:drive'`)? Finer = better forensics, more enum management. Recommend: finer-grained, matching the MCP method name 1:1.
