## Behavioral spec (one paragraph per part)

**(1) Migration payload preservation.** When porting v1 `scheduled_tasks` to v2 `messages_in` rows (`kind='task'`) via `setup/migrate-v2/tasks.ts`, the content-JSON payload must include `model` (preferred-provider override) and `suppress_chat_output` (delivery-gate flag), in addition to the existing `prompt`, `script`, `migrated_from_v1` fields. The V1Task SELECT must also expand to include these columns. Without (1), the runtime can't honor what doesn't reach v2.

**(2) Runtime honoring of preserved fields.** v2's scheduling executor reads `model` from the task content-JSON and passes it as a per-message model override to container-runner (interacts with C1's fallback model resolution — order: message `model` > group `containerConfig.model` > `DEFAULT_MODEL`). Similarly reads `suppress_chat_output` and uses it as the delivery gate (see Part 3 for the gate's actual mechanism).

**(3) Transitive output suppression.** The fix surfaces at v2's **outbound delivery layer** in `src/delivery.ts`, NOT at the agent's `send_message` call sites. Mechanism: when a session is processing a scheduled task with `suppress_chat_output=true`, the delivery loop suppresses ALL outbound `kind='chat'` rows for that session-run window EXCEPT the final result (last `chat` row before container exit OR rows tagged with a "final result" marker). Subagent outputs in v2 route through the agent-to-agent module (`src/modules/agent-to-agent/agent-route.ts`) — those are already user-suppressed (see `delivery.ts:200` comment "user doesn't see those"). The leak observed 2026-05-15 (Israeli News, NYT, CNN, BBC subagent dumps reaching Telegram) was from the **parent agent's intermediate `send_message` calls** during multi-subagent orchestration, not from the subagents themselves. v1's guard only fired on the scheduler's final delivery — the agent's intermediate `chat` outbounds bypassed it. v2's gate must apply to every outbound the task's session emits, only releasing the final result. Implementation: a flag on the task session in `inbound.db` (or session metadata) that `delivery.ts:deliverMessage` consults; rows are either suppressed (logged + marked-delivered-virtually) or queued for end-of-run release.

**(4) Window-age cap.** When the daily-update task reads `last_update_sent_at` from `groups/<group>/daily_update/config.json` for the digest-window-start computation, it must clamp the anchor to **no older than 48 hours before "now"**. The 2026-05-15 production blowout: a 14-day failure streak (May 1–14, credit-fallback breakage) left the anchor at April 30; the first successful post-hotfix run inherited that anchor and produced a 15-day catch-up digest with stale news from prior weeks. Implementation options: **(a) prompt-level clamp** — read the anchor in the task prompt's window-computation logic and apply `max(anchor, now - 48h)` before passing the window start to subagents (faster to ship; lives in the prompt JSON); **(b) generic scheduling "stale anchor" guard** — a v2-config-level feature that applies the clamp uniformly to any task using a watermark file (right long-term; bigger lift). **Recommend (a) now, (b) later** — Porter writes a one-line clamp in the prompt's window-computation step at migration cutover; revisit (b) if more watermark-anchored tasks emerge.

## Decisions / open questions
1. **End-of-run "final result" detection** (Part 3): how does the delivery gate know which `chat` row is THE final result? Options: (a) container emits an explicit `final_result` marker on the last outbound, (b) gate accumulates ALL chat outbounds and only releases the last one when container exits, (c) only suppress non-terminal rows (anything before container exits is intermediate). **Recommend (b)** — buffer + release-on-exit; matches v1's "deliver only the scheduler-side final" pattern. Container changes needed: none. Delivery state: a per-session "pending final" queue cleared on exit.
2. **Granularity of suppression** (Part 3): suppress all `kind='chat'` or also `kind='card'`, `kind='ask_question'`, etc.? v1 only suppressed `sendMessage` (text chat). **Recommend chat-only** for parity; revisit if production shows leaks via other kinds.
3. **Window cap value** (Part 4): 48h is a guess. Empirically: daily updates run every 24h, so 48h gives one missed-day buffer. Too short = lossy after planned downtime; too long = inherits the bug. **48h is reasonable; revisit if planned weekly downtime emerges**.
4. **Cap mechanism in (4)**: prompt-level (a) means every daily-update copy/clone needs the clamp added. Generic config-level (b) means the clamp is invisible to task authors. The right choice depends on how many tasks use watermark files — currently one (daily-update). Recommend (a) for now.
