## Behavioral spec (one paragraph)
When an inbound voice message arrives on any registered channel (WhatsApp `audioMessage.ptt=true` via Baileys, or Telegram `message:voice` via grammY), the channel adapter downloads the audio buffer (`downloadMediaMessage` / Bot API `getFile`+fetch) and routes it through a **channel-agnostic** `transcribeAudioBuffer(buffer): Promise<string|null>` helper. The helper tries local faster-whisper first (subprocess to `scripts/whisper_transcribe.py`, 60s timeout, `WHISPER_PYTHON` interpreter override allowed); on null/error it falls back to the OpenAI Whisper API (`whisper-1`, `response_format: 'text'`, key from `OPENAI_API_KEY`); on full failure it returns the fixed string `[Voice Message - transcription unavailable]`. The transcript replaces the otherwise-empty message content before storage/routing so the agent receives voice notes as text. Reason: zero-cost path when local works, reliable fallback when it doesn't, and unified surface across channels — voice notes are first-class user input.

## Decisions / open questions
1. **Local-whisper backend on Linux: KEEP v1's faster-whisper Python (decided 2026-05-19).** Already working on production Linux server; switching to upstream's `whisper-cli` requires building whisper.cpp from source (Homebrew path is macOS-only); faster-whisper + CTranslate2 + int8 is competitive with whisper.cpp on CPU; transcription is a leaf utility so divergence cost is low. **Revisit when the Mac mini comes online** (see `reference_home_network.md`) — upstream's `whisper-cli` becomes the natural path then; swap is a one-file change in `transcription.ts`.
2. **Helper module placement: v2 core (`src/transcription.ts`).** The channel-agnostic `transcribeAudioBuffer(buffer)` is called by both WhatsApp and Telegram adapters, so it has to live somewhere both can import — only v2 core qualifies.
3. **OpenAI API key wiring: RESOLVED 2026-05-19.** v2's `src/env.ts` exposes `readEnvFile(keys: string[])` — API-identical to v1's helper (same `.env` lookup in `process.cwd()`, same opt-in pattern, deliberately does NOT load to `process.env` to prevent child-process leakage). v1's call `readEnvFile(['OPENAI_API_KEY'])` transfers verbatim. Transcription stays host-side (audio buffer lives in the channel adapter before container dispatch) so OneCLI's container-side secret-injection path is irrelevant here.
