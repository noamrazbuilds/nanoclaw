## Source (v1)
- Primary: `docs/v1-fork-reference/src/image.ts` (93 LOC; exports `isImageMessage`, `processImage`, `isStickerMessage`, `processSticker`, `parseImageReferences`)

## Behavioral spec (one paragraph)
When an inbound WhatsApp message carries `imageMessage` or `stickerMessage` (Baileys protobuf), the channel adapter downloads the binary buffer via `downloadMediaMessage(msg, 'buffer', {})`, normalizes through `sharp` (images: resize to 1024px max via `fit: 'inside', withoutEnlargement: true`, jpeg quality 85; stickers: `.webp → .png` via `sharp().png()`), writes the file under `groups/<folder>/attachments/<filename>` (filenames `img-<ts>-<rand>.jpg` or `sticker-<ts>-<rand>.png`), and replaces the message content with a marker string: `[Image: <relativePath>] <caption>` or `[Sticker: <relativePath>]`. Downstream, `parseImageReferences()` extracts these markers from the message stream and yields `{relativePath, mediaType}` pairs (jpeg for images, png for stickers), which the agent dispatch pipeline reads back into base64 multimodal vision content blocks. The reason: photos and stickers carry conversational meaning the agent must see directly — particularly stickers (27 received / 15 days / 8 groups in production since 2026-04-29, ~2/day average, often EMS volunteer or family/friend chats where stickers ARE the message).

## Decisions / open questions
1. **Telegram image/sticker:** OUT OF U2 SCOPE. v1's Telegram adapter doesn't process inbound images/stickers as vision content (only voice via U1 and documents via the file-attachment path). If Telegram vision parity ever becomes a goal, that's a separate spec — not blocking here.
2. **GROUPS_DIR path layout:** Verify at spec extraction that v2's `GROUPS_DIR` resolves to the same `groups/<folder>/attachments/` layout v1 uses. If v2 reorganized group folders, `processImage` / `processSticker` paths need adjusting (the upstream image-vision skill presumably handles this — confirm by inspecting the skill's `path.join(GROUPS_DIR, ...)` call after merge).
3. **`parseImageReferences` extension:** v1's sticker line adds `mediaType: 'image/png'` for sticker refs. Upstream's pattern returns `'image/jpeg'` unconditionally (skill comment: *"Always JPEG — processImage() normalizes all images to .jpg"*). The extension must add a parallel sticker loop with `image/png`, not just relax the existing loop.
