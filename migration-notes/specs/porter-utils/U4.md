## Behavioral spec (one paragraph)
On NanoClaw host startup, `startOAuthRefreshMonitor(notify)` is called from `src/index.ts`. It reads the OAuth credentials from `~/.claude/.credentials.json` (the SDK's standard location), runs an immediate refresh check, then sets up a periodic check (`CHECK_INTERVAL_MS`, likely 30 min or 1h — verify at port time). The check inspects `expiresAt`; if remaining lifetime is under a threshold (likely 30 min), it POSTs to `platform.claude.com/v1/oauth/token` with the refresh token, optionally routing the request through `OAUTH_PROXY_URL` (SOCKS5) if set. On success, it writes the new credentials back to the file AND updates `ANTHROPIC_AUTH_TOKEN` in `.env`. The `notify` callback is invoked on errors that need user attention (e.g., refresh token expired, requiring manual `claude setup-token`). The reason: Anthropic's Claude Max OAuth tokens have a finite lifetime (currently 8h); without auto-refresh, the agent silently stops working when the token expires. v2's native error message "Re-run `claude setup-token` manually on 401" pushes the user into a manual-recovery loop — a failure mode the fork's daemon eliminates by maintaining the token continuously.

## Decisions / open questions
1. **SOCKS5 proxy code retention**: keep or strip? Retired per memory, but [[reference_oauth_proxy_setup]] explicitly says "code in `src/oauth-refresh.ts` still supports a proxy via `OAUTH_PROXY_URL` if needed in the future." **Recommend keep** — ~10 LOC of conditional code, low-risk, valuable if Cloudflare-block returns.
2. **`isCreditError` decoupling**: per C1 spec, port to `src/credit-error.ts` so C1 isn't blocked on U4. **Recommend yes** — small refactor at port time, removes a load-bearing transitive dep.
3. **Check interval**: v1 uses a constant (likely `CHECK_INTERVAL_MS = 30 * 60_000`, 30 min — verify at line ~20). Reasonable; preserve.
4. **`updateEnvToken` writeback safety**: v1 writes to `.env` directly via `fs.writeFileSync`. With concurrent setup-time edits possible, this is a small race. v1 hasn't shown problems in production; preserve. If a real corruption case emerges, add a lock file.
5. **Credential file race vs. external tools**: SDK clients (`claude code`, `claude setup-token`) also write to `~/.claude/.credentials.json`. v1's `getOAuthToken()` always reads fresh from disk to pick up external writes — preserve this pattern (do NOT cache the token in memory beyond the read).
