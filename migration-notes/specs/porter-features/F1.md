## Behavioral spec (one paragraph)
A self-contained Telegram bot bouquet running on the NanoClaw host (not in agent containers). Six grammy `Bot` instances, one per arena bot token, all polling the same Telegram chat (`-1003935516896`) independently. When a message arrives, the `ArenaOrchestrator` (in `index.ts`) routes it three ways: **broadcast** (no mention → all six bots respond in parallel), **targeted** (`@nanoclaw_X_bot` mention → only that bot responds), **reply-to** (user replies to a specific bot's earlier message → only that bot continues the thread). Bot responses are dispatched via LiteLLM HTTP (`http://localhost:4000`), with model routing per bot, staggered sends (`SEND_STAGGER_MS=200`) to avoid Telegram rate limits, and conversation history reconstructed via a `parent_log_id` chain in `arena_logs`. User reactions (👍/👎) on bot messages are captured and stored as `arena_log` rating fields. **Cron-driven grading**: at 2 AM daily, an Anthropic `claude-sonnet-4-6` grader (constant from C2, locked at fork commit `ddf53bb` for 5× cost reduction) reads the previous day's broadcast sessions, scores each bot's response on multiple axes, writes to `arena_grades`. **Weekly reports**: at 8 AM Friday, `arena-report.ts` reads aggregates and posts a summary to the same chat. The reason this exists: empirical multi-model comparison on real-world questions, with user ratings as ground truth and Claude as a per-session grader. Production-running since 2026-04-13.

## Decisions / open questions
1. **DB host: separate `arena.db` vs. v2 central `v2.db`** (the architectural OQ):
   - (a) Separate `arena.db` file in v2's data directory. Self-contained module, clean boundary, no impact on v2 core migrations, easy to drop/disable. Mirrors how v1 used `messages.db` as a sibling of everything else.
   - (b) Fold the 4 arena tables into `v2.db` via new migration (`src/db/migrations/<NN>-arena.ts`). Consistent with v2's other modules (`agent-to-agent`, `approvals`, `scheduling` all use the central DB), backups are simpler.
   - **Recommend (a) separate `arena.db`** — arena is a fundamentally optional, self-contained feature; mixing 4 tables into the core schema invites coupling. Cost: small (one extra `better-sqlite3.Database(...)` open).
2. **Cron mechanism**: keep arena's own scheduler (node-cron) vs. delegate to v2's `src/modules/scheduling/`?
   - v2's scheduling module is designed for **agent-driven** tasks (the agent creates scheduled tasks via MCP tools). Arena's cron is **system-driven** (grading, weekly reports) — different shape. **Recommend keep arena's own cron** (`node-cron` or `cron-parser` equivalent) inside the module; simpler than re-shaping arena's grading loop to fit v2's task model.
3. **Memory list update**: [[project_model_arena]] says 5 bots; actual count is 6 (Sonnet is the 6th, added later). Update post-port.
4. **Local model timeout config**: `LOCAL_MODEL_TIMEOUT_MS = 600_000` (10 min) reflects 1vCPU constraint. Verify v2 host has the same hardware profile (Pi vs Mac mini matters — see [[plan_definitely_yes_integrations]]); if Mac mini lands, this could drop to 60s.
5. **Per-channel reaction wiring**: arena writes to its own `arena_logs.rating` field, separate from F6's general `reactions` table. Reactions on arena bot messages are captured via grammy's own reaction event (not the WhatsApp `messages.reaction` path of F6). No coupling.
