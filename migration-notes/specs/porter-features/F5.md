## Behavioral spec (one paragraph per ported tool)

**`register_group`**: Main group only. Args: `jid` (chat JID), `name` (display name), `folder` (channel-prefixed folder name like `whatsapp_family-chat`), `trigger` (trigger word, e.g. `@Andy`). Writes an IPC file (`writeIpcFile(TASKS_DIR, {type:'register_group', ...})`) that the host reads and processes — host creates the group folder, adds the trigger pattern, starts listening for messages on that JID. Returns synchronously after the IPC write; the agent doesn't wait for confirmation. The reason: lets the user (via the main agent in the main group) add new chat groups conversationally — "Hey, register the chat `120363336345536173@g.us` as `whatsapp_family-chat` with trigger `@Andy`" — without needing to drop into a setup flow. **Restricted to the main group** because the act of registering a new group has admin scope (it's adding to the agent's listened-channels set).

**`generate_image`**: Args: `prompt` (description), `caption` (optional text caption), `size` (one of `1024x1024` / `1792x1024` / `1024x1792`, default `1024x1024`). Calls `LITELLM_HOST/v1/images/generations` with `model: 'gpt-image-2'` (per memory [[plan_definitely_yes_integrations]] section 4, model may have been updated since — verify at port time). LiteLLM returns image data; the tool delivers it directly to the chat via IPC (file write to the outbound dir), so the agent does NOT need a separate `send_message` call. The reason: image generation is a high-utility user request; bundling generation + delivery into a single MCP call removes a frequent "I generated the image, now I need to send it" two-step pattern that was confusing the agent.

## v2 hook point(s)
- **Pattern**: follow v2's existing mcp-tool registration pattern — each tool is an exported `McpToolDefinition` with `name`, `description`, `inputSchema`, `handler`. Modules call `registerTools([...])` at import time. See `container/agent-runner/src/mcp-tools/scheduling.ts:302` for the canonical template.
- **`register_group`** → new file `container/agent-runner/src/mcp-tools/registration.ts`. Tool exports `registerGroup`. Handler: emit an outbound message with a new kind (e.g. `kind: 'register_group'`) OR write to a dedicated IPC dir — see OQ#1. v2 main has `register_agent` (in `agents.ts`) but that's for AGENT groups (`agent_groups` table); `register_group` is for MESSAGING groups + bot listening + trigger setup. Different concern.
- **`generate_image`** → new file `container/agent-runner/src/mcp-tools/image-gen.ts`. Tool exports `generateImage`. Handler: call LiteLLM, write the resulting image as an outbound `kind: 'chat'` with a `files: [...]` attachment (matches v2's outbound vocabulary). LiteLLM URL: read from container env (`LITELLM_HOST`), default `http://host.docker.internal:4000`. LiteLLM key: OneCLI vault injection.
- **Main-group gate** for `register_group`: how does v2 know "this is the main group"? Check `isMain` on session or agent-group config. Find the equivalent of v1's `isMain` runtime flag in v2's session-state.

## Decisions / open questions
1. **`register_group` outbound mechanism**: v1 wrote to a dedicated IPC dir (`TASKS_DIR`). v2's outbound vocabulary is `chat | edit | reaction | ask_question | card` + optional `files`. Options: (a) introduce a new outbound `kind: 'register_group'`, host reads + acts on it, (b) reuse `kind: 'system'` with structured action payload, (c) call a host-side endpoint directly (HTTP/socket). **Recommend (a)** — explicit kind matches v2's structural-discriminator pattern. Add to the outbound vocabulary docs.
2. **`generate_image` model name**: v1 hardcodes `'gpt-image-2'`. Memory [[plan_definitely_yes_integrations]] section 4 mentions `gpt-image-1` (OpenAI's released model). The v1 fork may be using a future/internal name. **Verify at port time** — pull the current LiteLLM config to see which model name is registered; adapt the constant.
3. **Image attachment delivery**: v1 inlined the IPC write inside the tool handler (one-step generate-and-deliver). v2's outbound `kind: 'chat'` with `files: [...]` is the equivalent. Implementation: tool handler decodes the base64 LiteLLM response, writes the image to the session's attachments dir, emits the outbound row pointing at it.
4. **Main-group restriction enforcement**: in v1, the tool itself checks `if (!isMain) return error`. v2 could (a) reuse that pattern (check session metadata), or (b) gate via tool-registration: only register `registerGroup` for main-group sessions. Option (b) is cleaner — the tool isn't discoverable if you can't call it. Recommend (b).
5. **Queue clarification** (procedural): the F5 row currently lists `host_op` as in-scope. Audit shows it's not an MCP tool — it's U5c scope. Worth a queue-row clarification (similar to unlock-3's U2 clarification + F6 phantom finding). Could be folded into a future unlock or left as the spec's correction-of-record.
