## Behavioral spec (one paragraph)

When a WhatsApp user adds or removes an emoji reaction on a message (Baileys `messages.reaction` event), the adapter resolves the chat JID (LID→phone via `translateJid` when applicable), skips `status@broadcast`, filters to registered groups, and writes the reaction to a `reactions` SQLite table keyed by `(message_id, message_chat_jid, reactor_jid)` — an empty emoji `DELETE`s the row, a non-empty emoji `INSERT OR REPLACE`s it. Outbound, the container agent calls the `react_to_message` MCP tool (emoji + optional `message_id`; omitting it means "latest message in the chat", empty emoji removes the bot's reaction); the tool writes a `type:'reaction'` IPC frame, the host's IPC watcher authorizes it against the source group and calls the channel's `sendReaction`/`reactToLatestMessage`, which emits a Baileys `react` payload. The reason: emoji reactions are first-class lightweight signal in WhatsApp culture both ways — users react to acknowledge/agree/emote, and the agent reciprocates to feel responsive without sending text.

## Decisions / open questions

1. **The ported `src/channels/whatsapp.ts` is the only file a v2 install fetches — and as ported it would BREAK a v2 install, not merely lack a backend. v2-core threading is a prerequisite for shipping it to v2, not optional follow-up.** `nanoclaw-v2` has no `src/db.ts`, `src/ipc.ts`, `src/index.ts`, or single-file `ipc-mcp-stdio.ts`; the `add-whatsapp` skill fetches only `src/channels/whatsapp.ts` + `image.ts` + setup from the fork. The ported `whatsapp.ts` now `import { …, getLatestMessage, storeReaction } from '../db.js'` — symbols that exist in the **fork's** `src/db.ts` but have no v2 counterpart, so copying this file into v2 as-is would fail import resolution and break the WhatsApp adapter's compile/runtime. **Timing safety:** `porter-F6` is local-only and `whatsapp-fork/main` does not yet contain this port, and the in-repo `add-whatsapp` skill fetches from `whatsapp-fork/main` — so **no current v2 install is affected**; the breakage risk only materializes if the port is pushed to fork `main` before the v2-core thread lands. The follow-up v2-core task must add, together as a unit: a reactions table to v2's session/central DB layer, the `getLatestMessage`/`storeReaction` equivalents v2's `whatsapp.ts` will import, a `react_to_message` tool in `container/agent-runner/src/mcp-tools/`, and reaction delivery in `src/delivery.ts`. Do **not** mark reactions "shipped in v2" on the strength of this row, and do **not** push `porter-F6` to fork `main` until that thread is ready. Revisit at Checkpoint A (Batch-1 end-to-end wiring).
2. **DB migration timing.** `scripts/migrate-reactions.ts` is ported verbatim (creates the table in `store/messages.db` for the fork's own runtime). v2 uses `src/db/migrations/`; the v2-threading task in #1 should add a v2-native migration rather than invoking this script. Kept here so the fork stays self-consistent.
3. **No new dependencies.** Reactions reuse `better-sqlite3` + `@whiskeysockets/baileys`, already in the fork. The verify script asserts both `package-lock.json` files are byte-identical to `whatsapp-fork/main`; a diff there is a blocker.
4. **Tests not ported.** `skill/reactions` carries ~2k lines of test churn rebased on a stale base and entangled with U3. Per U1/U2 precedent, feature code is ported and the gate is `tsc --noEmit` + the snippet verify + manual smoke; the v1 test files are not transplanted.
