## Behavioral spec (one paragraph)
AnyList MCP exposes shopping-list / recipe / meal-planning tools to the agent (add ingredient, get items, check meal plan, etc.). Architecturally it's a long-lived stdio MCP server: the agent's MCP client spawns the server process at container start, the server stays up for the session, the agent invokes tools over stdio. The server authenticates to AnyList's backend on first call using `ANYLIST_EMAIL` + `ANYLIST_PASSWORD` env vars (sourced by `run.sh` before exec'ing the Node entrypoint). The reason this exists: shopping/recipe/meal data is high-utility household-management state — moving it through the agent's tool surface lets the user say "add X to the grocery list" or "what's for dinner Thursday?" in any channel without switching apps. The vendor source is deliberately frozen on the host (not auto-updated) because the AnyList API is unofficial and breaking changes can cascade into the household's daily-life infrastructure; updates require manual re-vetting.

## Decisions / open questions
1. **Bundle in container image vs. mount via `additional_mounts`** (the central OQ):
   - **(a) Bundle in image at build time** via `container/Dockerfile`. Clean, single artifact, fast container startup. Cost: vendor updates require image rebuild (~5–10 min); image size grows by ~30MB (node_modules dominates).
   - **(b) Mount from host** via `container_configs.additional_mounts: [{"host": "/path/to/vendor/anylist-mcp", "container": "/workspace/project/vendor/anylist-mcp", "readonly": true}]`. No rebuild on vendor updates; matches v1's pattern. Cost: host path management; multi-host installations need parallel update.
   - **Recommend (b)** — vendor-update flexibility matters (AnyList API breaks more frequently than container image rebuilds happen). The MCP source path stays `/workspace/project/vendor/anylist-mcp/run.sh` — matches v1's container-runner-rewritten path. Bundle (a) is the right move if the production server moves toward an "immutable image" deployment model.
2. **Credential delivery mechanism**: OneCLI vault injection (proxy-side) vs. `.env`-style file in the container.
   - **Recommend OneCLI vault** for parity with how `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` work. The `run.sh` wrapper's `.env` sourcing becomes a no-op (file absent), and the env vars are present in `process.env` via OneCLI's proxy injection. Verify with [[reference_onecli_secret_management]].
3. **Vendor source location**: where in v2's tree? Options:
   - (a) `vendor/anylist-mcp/` at repo root (matches v1 layout).
   - (b) `container/skills/anylist-mcp/` (treat as a container skill).
   - **Recommend (a)** — vendor third-party code traditionally lives in `vendor/`; treating it as a "skill" mixes vendor-provided code with first-party skill manifests. Cleaner to keep separate.
4. **GitHub re-vetting cadence**: AnyList MCP is an unofficial integration with security-sensitive credentials. Memory says it's vetted but intentionally not auto-updated. Reaffirm post-port that the same discipline holds in v2 — no GitHub auto-update workflow, manual re-pin only.
